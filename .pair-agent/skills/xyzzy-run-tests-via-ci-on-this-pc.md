## 規則

- **手元で `run-tests.bat` を流さない。** xyzzy の窓が利用者の画面に出る。全件試験は CI で流す（自分の試験だけなら、別デスクトップで `ci-test.ps1 -Tests` を流す。`xyzzy-verify-gui-on-a-separate-desktop` の「役が自分の試験を手元で流す」）
- CI の実体はこの PC（自己ホストのランナー。名前 `ANCIENT-xyzzy-fork`、ラベル `xyzzy`、Windows のサービス）。見えない画面で動くので窓・マウス・前面を奪わない。環境はこの PC のまま

## ファイル

- `.github/workflows/test.yml`: `feature/x64-only` と `develop` への push と手動実行で走る（役のブランチ `worktree-agent-*` では走らない）。**公開リポジトリなので `pull_request` では走らせない**（第三者のコードがこの PC で動く）
- `ci/ci-test.ps1`: `install.bat` → ダンプを書く起動 → `run-tests.bat` → 全件のときだけ `XYZZY_CHAR_UNICODE=1` でのビルドとリンク（[4/4]）
- `ci/install-runner.ps1`: この PC をランナーとして登録しサービスに入れる。管理者で 1 回。置き場所の既定は `%ProgramData%\actions-runner\<名前>`
- `ci/README.md`: 手順の詳細

## 結果の見方

- 一覧: `gh run list`
- 待つ: `ci/wait-run.ps1`（0 合格・1 不合格・2 まだ・3 実行なし）。**`gh run watch` や gh を繰り返し呼ぶ待ち方は使わない。** GitHub の API は 1 時間 5000 回でアカウントの共有。2026-11-22 に、役たちが数秒ごとに問い合わせて使い切り、全員の待ちが止まった。wait-run.ps1 は 1 分に 1 回、1 回の呼び出しで問い合わせ、上限に当たると戻る時刻まで待つ（戻る時刻は `gh api rate_limit` で見る。これは回数に数えられない）
- ログ・成果物: `gh run download <id> -n test-logs`
- 手動で起こす: `gh workflow run test.yml --ref <ブランチ>`
- **時間切れ**: 1 回の実行は約 5 分。`ci-test.ps1` の各段（install・run-tests・1 側のビルド）は 20 分、ジョブ全体（`timeout-minutes`）は 40 分で切る。以前の 60 分のときは、止まった試験 1 本（BUG-0060）が唯一のランナーを 61 分ふさいだ
- **待ち行列の順は当てにしない**（2026-11-22 の観測）。ランナーは 1 台。待っている実行のうち新しく入ったものから先に拾い、17:35 から待っていた R4・R1 の実行が後から入った push に 1 時間半抜かれ続けた。親が待ちの実行を取り消して古い順に再実行し、解けた。同じブランチの新しい push は古い実行を取り消す。文書だけの変更（`*.md`・`docs/`・`bugs/`・`.pair-agent/`）と `[skip ci]` では走らない

## 役は CI を待たない（師匠の指摘 2026-11-22・21:15 から適用）

師匠の言葉（原文 2026-11-22）:

> ３時間以上はあまりにも遅すぎる。進め方の設計が根本的に悪い

- 段 3 で、役が全件 CI の待ちを抱えて 1 スライス 3〜3.5 時間かかった。**役は CI を待たない。** 上の「（外した）役のブランチでも CI を流す」は、この節で置き換えた
- 役の門は手元の周: **増分ビルド + 自分の試験だけ**を、別デスクトップ（deskrun。`xyzzy-verify-gui-on-a-separate-desktop`）で流す。秒で回す。`XYZZY_CHAR_UNICODE=1` 側の Rebuild も役はしない
- **CI は統合の門。** 親が部品を束ねて統合し、統合の CI を 1 回流す（1 側のビルドもここで確かめる）。落ちたら落ちた部品だけを差し戻す
- 仕事は 30 分以内の部品（関数 1 つかファイル 1 つ）に割って並列に起こす。一般の規則はペア固有 Skill `small-parallel-parts-fast-local-loop-ci-only-at-integration`
- **統合の衝突は、追記だけの一覧 `lisp/builtin.l` と `src/gen-syms.cc` にいつも出る**（並列の部品がそれぞれ関数を足すため）。両側の行を残せば正しい（段 3 の R9 の統合で R3・R10 の追記とぶつかり、両方を残して、統合した木で R3・R9・R10 の試験 46 件が合格した）。ほかのファイルの衝突は、どちらの版が新しい仕組みに合うかを見て選ぶ（R1 の `disp.cc` の 1 行は R1 の版を採った）

## つまずいた点（再発させない）

- ランナーを `C:\Users\<名前>\…` の下に置くとサービスのアカウント（NETWORK SERVICE）が上の階層を読めず起動しない。`%ProgramData%` 側に置く
