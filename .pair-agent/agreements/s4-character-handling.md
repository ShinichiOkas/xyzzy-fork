## ゴール

内部の文字を Unicode のコードポイントにし（判断 1）、Win32 とは UTF-16 でやり取りする（決定 2）。
文字の変換は一つのエンコーダ層に集め、ファイルは W 版 API で扱う。ソースは UTF-8 にする（判断 9）。

## 完了の基準（計画より）

- cp932 のファイルを開いて保存し、バイト列が同じ（S4-0 の試験。重複符号の扱いは設計書で決め、事後報告）
- 非 cp932 の文字のファイル名を開ける（4b の後で試験を置く）
- 文字の試験が通る。全件テストが合格（基準は 637 件。増えた試験は内訳を報告）
- S4-c の基準: 260 文字を超えるパス、4GB を超えるファイルのサイズ、8.3 の処理の削除、既存の試験

## リスク

- Char（u_int16_t）は 95 ファイル・1520 箇所。pathbuf_t も Char なので、S4-c と拡幅を同時に走らせない
- cp932 の重複符号（NEC の 13 区と JIS の記号、NEC 選定 IBM 拡張と IBM 拡張）は Unicode を経ると往復で変わる。設計書で方針を決める
- ダンプイメージと .lc の形式が変わる（ビルド時に作り直すので可。判断 3）
