# BUG-0056 否定の文字クラス `[^…]` が、文字の上位バイトがクラスの範囲にある文字に当たらない

- 状態: 未修正（2026-11-22）
- 対象: x64 版（feature/x64-only、5e40677）。x64 固有ではないと見られる（拡幅の前の 16bit の Char でも起きる）
- 起票: 2026-11-22（S4 の段 2「W」の試験を書いていて見つけた。調べていない）

## 症状
- 内部の符号が 0x0100 以上の文字のうち、「上位バイト（符号 >> 8）」が否定のクラスの範囲に入る文字は、`[^…]` に当たらない。クラスに書いた範囲にその文字は入っていないので、当たるのが正しい。
- 確かめた結果（全部の符号 0〜65535 を 1 文字の文字列にして `string-match`。期待は「範囲の外なら当たる」）:

| 正規表現 | 当たらない符号（期待と違うもの） |
|---|---|
| `[^?-_]`（0x3F〜0x5F） | 0x3F00〜0x5FFF |
| `[^a-z]`（0x61〜0x7A） | 0x6100〜0x7AFF |
| `[^A]`（0x41） | 0x4100〜0x41FF |
| `[^ -~]`（0x20〜0x7E） | 0x2000〜0x7EFF |

- 肯定のクラス（`[?-_]`、`[a-z]`、`[ -~]`）は、全部の符号で期待どおり。
- たとえば `(string-match "[^A]" (string (code-char #x4142)))` が nil（期待は 0）。

## 再現
```lisp
(string-match "[^A]" (string (code-char #x4142)))   ; => nil
(string-match "[^A]" (string (code-char #x4200)))   ; => 0
```
